# An unsaved definition draft survives other changes (2026-10-18)
Found in the whole-app UI review of main. With a server's definition edited in the form or as JSON but not yet saved, any other change applied (turning that server off from the toolbar, duplicating it, approving another) re-read the definition and replaced the draft with what was saved. The edit was gone without a word. Seen in the real app: the command changed to `python33`, the server turned off, and the form said `python3` again.
- `shell.rs`: on `Applied`, the open editor is read again only when its draft has no edits, or when the plan applied is the one that saves this draft. Otherwise the draft stays as it is. Which plan saves the draft is known from the save bar: it sets `draft_asked` when it sends the `Replace`. The next `PlanReady` turns that into `draft_plan` (its id), and `PlanFailed` clears it. A review that was cancelled never matches a later plan's id. `EditorState::edited()` syncs the form and JSON first, then compares the draft with what was read.
- Why read back after its own save: what was written is shown as the file has it (secrets masked again), and typed values are dropped from memory.
- Tests: `a_draft_not_yet_saved_survives_another_change_being_applied`, `a_draft_edited_as_json_survives_another_change_being_applied`, `a_draft_whose_review_was_cancelled_or_failed_survives_a_later_change` (all three seen failing first against main). `a_saved_draft_is_read_again_once_applied` passes on main, so it was checked by mutation: with `saved_draft` forced false it fails. With `PlanFailed` not clearing `draft_asked`, the cancelled-or-failed test fails. `after_a_save_the_definition_is_read_again` (an unedited form is read again) still passes.
