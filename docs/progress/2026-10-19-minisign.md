# minisign signature on SHA256SUMS (2026-10-19)
Goal: M4 slice 3 of 6. Sign each release's `SHA256SUMS` with minisign, so users (and later Klefki's own update
check, slice 6) can verify a download offline with one public key. The key is the owner's; this slice builds
everything up to it. Branch `claude/packaging-release-407cg1`, restarted from main after #41.

- **Switched on by the public key.** `scripts/sign-checksums.sh` does nothing but print a notice until
  `minisign.pub` is committed at the root. After that, a missing `MINISIGN_SECRET_KEY` secret, a wrong password or
  a key that does not match `minisign.pub` fails the release. So no release can silently ship unsigned once
  signing is on, and none fails before the owner has a key.
- **Where it runs.** The publish job, after `SHA256SUMS` and before the provenance attestation (so the
  `.minisig` is attested too). Only on tags and manual runs from main: the key never reaches code from an
  unreviewed branch. The trusted comment names the ref and commit.
- **Key handling.** The secret key is written to a `mktemp` file under `umask 077`, removed by an EXIT trap; the
  password goes to minisign on stdin; neither is echoed.
- **Notes.** When a signature exists, the draft-release step appends `docs/release-notes-minisign.md` with the
  public key filled in (a `minisign -Vm SHA256SUMS -P <key>` command and what success prints).
  `docs/RELEASING.md` has the owner's four setup steps.

## Checks run
- Local, minisign 0.11, throwaway key (never committed): no `minisign.pub` → notice, exit 0; `minisign.pub` but
  no secret → error, exit 1; right key and password → `Signature and comment signature verified`, exit 0;
  wrong password → exit 2; a key that does not match `minisign.pub` → key-id mismatch, exit 1. A changed
  `SHA256SUMS` fails verification (exit 1). Notes assembly with the same `sed` puts the key in the command.
- `release.yml` parses as YAML.
